# Git 快照与业务数据回滚

## 两类恢复点

代码：sb-baseline-20261019 是施工前已验证基线，sb-T00-verified 是施工治理文档快照；每个功能新增 sb-Txx-verified，子功能增加 sb-Txx-01-verified。标签禁止移动。已授权本地 Git，不默认创建远程、推送或部署。

数据：Git 不保存 data.db、checkpoints.db、Chroma、上传文件、运行配置、.env。T10 必须实现一致性备份与恢复脚本；T10 前发生持久化/迁移变更，施工者必须先按下面的停写方法备份真实数据，否则不能执行可能破坏兼容性的迁移。

## A. 非破坏性检查旧版本

```powershell
git status --short
git show --stat sb-T03-verified
git rev-parse 'sb-T03-verified^{commit}'
# 新建隔离工作树，路径必须在用户允许的目录；使用已确认存在的 tag
git worktree add --detach ../smartbrief-rollback-check sb-T03-verified
```

工作区 dirty 时先明确文件归属，必要时作 wip 提交或备份，不覆盖现有文件。新工作树没有本地密钥与数据库：使用独立测试数据，不能接到正在运行的生产库。目录写权限不足按执行环境申请，不通过绕过权限删除文件。

## B. 回滚功能并保留历史

优先从当前分支新建修复分支，在确认数据兼容后执行 git revert <明确提交>（或经审查的反向范围），修复冲突，重新跑适用测试再提交。多次依赖提交须逆序评估，不能随意只回滚父模块。Git revert 不会自动把 task/state/日志语义修正：记录 rollback 事件，将受影响任务及后续任务标为待重验，更新 next_task 和 HANDOFF；保留旧快照与失败历史。

需要完全还原一组代码时，先在新分支/新工作树检出已验证 tag，再按下面流程恢复匹配的数据副本。禁止默认使用 reset --hard、git clean -fd、强推或删除标签。

## C. 一致性数据备份（T10 前人工执行原则）

1. 阻止新任务/评测，等待或取消在途工作；停止该实例后端与 MCP，确认没有写入进程。不要把在线运行中的 SQLite 和 Chroma 普通复制拼成“同一时点”备份。
2. 在仓库外新建只读保护的备份目录，复制业务库、检查点（存在 WAL/SHM 时一起保留）、完整 Chroma 目录、上传目录与三个非密钥运行配置。密钥单独安全保存，不进 Git 和常规备份包。
3. 清单记录 code_tag、SQLite schema_version、文件相对路径/大小/SHA256、备份时间/时区与停写方式；实际打开副本执行 SQLite integrity_check，并核对任务/日志/评测行数。
4. 备份完成且校验通过后才运行迁移。迁移脚本需可重复执行；涉及向量模型/维度变更时建立新集合和索引版本，不原地覆盖。

## D. 恢复与兼容

恢复到新目录或隔离卷，校验哈希/数据库完整性后，以匹配的 code_tag 和 schema_version 启动。验证报告读取、任务状态、RAG 检索、检查点恢复和配置后再切换实例；保留旧目录。旧代码无法读取新 schema 时，必须使用与旧代码匹配的数据备份，不能只 git checkout。

T10 的脚本必须把这些步骤自动化并在临时卷验证，不能将仅“复制成功”称作恢复成功。回滚与恢复均写入 dev-log，记录受影响任务和是否需要重验后续功能。

## E. 回滚后的再次施工

旧标签和旧凭据保留在原提交中，重新施工使用新后缀标签（例如 sb-T03-r2-verified）并在 state.json/凭据/任务表同步引用，不移动原 sb-T03-verified。每次失败输出使用 attempt-编号文件保留；后续成功不能覆盖失败历史。
